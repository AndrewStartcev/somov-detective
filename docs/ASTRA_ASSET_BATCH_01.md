# 6. Production-принципы

Ассеты создаются не как красивый общий арт, а для реального использования в игре.

Для персонажей и props:

- `PNG`;
- RGBA;
- прозрачный фон;
- чистый alpha;
- без белой/цветной подложки;
- безопасный transparent padding;
- не обрезать волосы, руки, ноги, хвосты и предметы;
- единый масштаб внутри набора одного персонажа;
- единая одежда, лицо, пропорции и палитра во всех позах;
- не менять дизайн персонажа от картинки к картинке.

Для spritesheet:

- кадры одного размера;
- одинаковая точка опоры персонажа;
- понятный порядок кадров слева направо;
- без перекрытия соседних кадров;
- transparent background.

Для UI:

- текст не впекать в кнопки и панели, если документ явно не требует обратного;
- состояния элементов делать раздельно;
- прозрачный фон;
- избегать современного SaaS/mobile-app вида.

# 19. Экономия токенов и image-generation бюджета

**Приоритет: максимальная экономия токенов и генераций без снижения качества production-ассетов.**

Не расходовать модель там, где задачу можно выполнить локально обычными инструментами.

## 19.1. Документацию читать один раз

В начале Batch 01 изучить обязательные документы и референсы, после чего работать по ним.

Не перечитывать все `.md` перед каждым новым изображением.

При необходимости уточнения открывать только:

- конкретный раздел нужного персонажа;
- конкретную локацию;
- нужную сцену;
- соответствующий visual reference.

Не пересказывать содержимое документов пользователю и не создавать собственные длинные summary-файлы.

## 19.2. Сначала master, потом производные файлы

Для одного персонажа не делать отдельную дорогостоящую генерацию на каждую позу, если их можно получить согласованным набором.

Предпочтительный pipeline:

1. взять утверждённый concept из `docs/assets/`;
2. создать один согласованный master/character sheet;
3. после проверки внешности создать **один или минимальное число production sheets на прозрачном фоне** с несколькими состояниями;
4. отдельные PNG вырезать из production sheet локально;
5. ресайз, crop, padding, переименование и упаковку выполнять локальными инструментами/скриптами без новой AI-генерации;
6. отдельно перегенерировать только кадр/позу, которая действительно не прошла контроль качества.

**Не перегенерировать целый sheet из-за одного плохого элемента, если технически возможно заменить только этот элемент.**

## 19.3. UI и props генерировать пакетами

Однотипные UI-элементы и небольшие props сначала создавать согласованными пакетами/листами с единым стилем.

После этого:

- нарезать локально;
- очищать alpha локально;
- делать размеры и padding локально;
- конвертировать формат локально;
- собирать preview локально.

Не использовать image generation для операций, которые являются обычной обработкой уже готового изображения.

## 19.4. Не создавать лишние preview

Для одного этапа достаточно **одного контрольного contact sheet / preview**.

Не создавать отдельный красивый mockup для каждого ассета, если он не нужен для проверки композиции или качества.

Production files важнее презентационных изображений.

## 19.5. Не дублировать уже готовое

Перед генерацией проверить папку назначения.

Если нужный файл уже существует и соответствует ТЗ:

- не создавать копию;
- не делать `v2`, `final2`, `new`, `better` без необходимости;
- использовать существующий production asset.

Если исправление нужно — менять только проблемную часть и сохранять понятную версию по существующей структуре.

## 19.6. Не тратить токены на длинное общение

Во время выполнения:

- не писать длинные промежуточные отчёты;
- не объяснять очевидные действия;
- не пересказывать ТЗ;
- не запрашивать подтверждение каждого следующего файла;
- не задавать вопросы, ответ на которые уже есть в документации или визуальных референсах;
- не предлагать дополнительные ассеты вне Batch 01.

Если возникает некритичная неоднозначность — выбрать вариант, который лучше соответствует `docs/assets/` и библии проекта, отметить решение одной строкой в `ASSETS_REPORT.md` и продолжить.

Остановиться и запросить решение только если неоднозначность реально может привести к массовой переделке уже созданных ассетов.

## 19.7. Приоритет расходования генераций

Если доступный бюджет ограничен, тратить его в таком порядке:

1. **Сомов** — главный персонаж и главный тест консистентности;
2. **Клавдия**;
3. **Горыныч**;
4. **core UI vertical slice**;
5. **ключевые props**;
6. дополнительные состояния и polishing.

Не начинать низкоприоритетный контент, пока более важный набор не приведён в production-ready состояние.

## 19.8. Checkpoint вместо повторной работы

После завершения каждого крупного набора:

- сохранить файлы сразу в правильные пути;
- проверить их локально;
- отметить статус в `ASSETS_REPORT.md`;
- не держать результат только во временном контексте модели.

Если сессия прервётся или закончится лимит, следующая сессия должна продолжить с последнего реально сохранённого файла, а не генерировать Batch 01 заново.

## 19.9. Главный принцип экономии

> **AI используется для создания нового визуального содержания. Обычные файловые операции, нарезка, упаковка, проверка размеров, конвертация и отчётность выполняются локально без лишних генераций.**

Экономия не должна приводить к:

- ухудшению консистентности персонажей;
- использованию плохого кадра только потому, что он уже создан;
- растягиванию одного изображения вместо корректной перерисовки;
- автоматической нарезке, если элементы реально перекрываются;
- production-файлам с грязным alpha или сломанной анатомией.

Если приходится выбирать между одной дополнительной генерацией и заведомо плохим production-ассетом — качество важнее.
