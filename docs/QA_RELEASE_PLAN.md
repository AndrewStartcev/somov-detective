# QA / RELEASE PLAN — «Дело о пропавшем четверге»

> Статус: **утверждённый pre-code план**  
> Версия: 1.0

Цель — заранее определить, как проверять игру, чтобы финальный этап не превратился в хаотичное исправление сцен, сохранений и SDK перед модерацией.

## 1. Уровни тестирования

### A. Content validation

Проверяем сюжет как систему:

- все обязательные улики достижимы;
- ни одна улика не требует знания, которого игрок ещё не мог получить;
- каждый `GATE` имеет минимум два честных подтверждения;
- нет логических противоречий между первым и вторым пропавшим четвергом;
- реплики персонажей меняются после ключевых фактов;
- ложные версии снимаются явно, но не чрезмерно;
- финал нельзя открыть до получения обязательных доказательств;
- после обнаружения якоря нет искусственного затягивания.

### B. Interaction validation

Для каждого hotspot:

- корректный курсор/подпись;
- понятная interaction point;
- правильная реакция до/после сюжетного изменения;
- неправильный предмет не ломает state;
- нельзя повторно забрать уже полученный предмет;
- повторный клик не дублирует важную награду.

### C. Save/load

- перезагрузка страницы после каждой крупной сцены;
- выход в меню после puzzle completion;
- закрытие вкладки после clue acquisition;
- загрузка после перехода акта;
- загрузка после получения квитанции;
- загрузка после открытия ячейки;
- завершённая игра корректно показывает completed-state;
- reset действительно начинает новое дело, не оставляя старые flags.

### D. Platform

Отдельно для Local, Яндекс, Пикабу.

# 2. Canonical walkthrough

Перед релизом должен существовать один официальный walkthrough для QA.

Он включает:

- минимальный обязательный маршрут;
- все puzzle solution steps;
- условия открытия каждой сцены;
- все обязательные dialogue topics;
- расположение предметов;
- expected Story State после каждого акта.

Этот walkthrough пишется после реализации content data, но его структура уже задаётся `DETECTIVE_GRAPH.md` и `PUZZLES.md`.

---

# 3. Проверка альтернативного порядка

Поскольку ранняя часть игры полуоткрытая, отдельно тестируем:

1. Редакция → Котельная → Архив.
2. Архив → Редакция → Котельная.
3. Котельная → Архив → Редакция.
4. Игрок сначала делает все доступные побочные задачи.
5. Игрок игнорирует все необязательные задачи.
6. Игрок многократно возвращается в старые локации.

Любой порядок должен приходить к одному корректному `GATE-01` без дубликатов фактов и сломанных реплик.

---

# 4. Puzzle QA

Для каждой головоломки проверяем:

- решение без подсказки;
- hint level 1;
- hint level 2;
- неправильные действия;
- повторное открытие puzzle UI;
- закрытие UI без решения;
- reload во время/после puzzle;
- touch interaction;
- крупный текст;
- отсутствие скрытого pixel hunting.

### UX-метрика

Если несколько независимых тестировщиков застревают в одном месте не из-за дедукции, а из-за непонимания интерфейса — исправляем интерфейс, а не добавляем более прямую текстовую подсказку поверх плохого UX.

---

# 5. Диалоги

Проверить:

- нет текста за границами панели;
- длинная фамилия/имя помещается;
- быстрый клик сначала раскрывает строку, затем переключает;
- невозможно случайно пропустить важный state effect двойным кликом;
- topic не исчезает до получения результата;
- exhausted topic ведёт себя одинаково после reload;
- текст не зависит от недоступного будущего факта;
- опровергнутые версии корректно отражаются в блокноте.

---

# 6. Mobile QA

Минимум:

- Chrome Android;
- Яндекс Браузер Android;
- Safari iOS;
- несколько соотношений сторон в landscape;
- portrait orientation message;
- системное масштабирование/крупный текст, насколько применимо.

Проверяем:

- touch target;
- hotspot hitboxes;
- отсутствие hover-only информации;
- UI safe margins;
- клавиатура не требуется для прохождения;
- панели не перекрывают критические объекты;
- переходы не вызывают случайный второй tap;
- возвращение из background не ломает звук/анимации.

---

# 7. Desktop QA

Минимум:

- Chrome;
- Яндекс Браузер;
- Safari macOS, если доступен;
- распространённые размеры от небольшого ноутбука до 1080p/1440p.

Проверяем:

- курсоры;
- hover states;
- масштабирование;
- fullscreen/windowed behavior;
- browser zoom edge cases;
- клавиатурные системные действия не ломают игру.

---

# 8. Performance

Цель — стабильная 2D-игра без тяжёлых сцен.

Проверяем:

- стартовую загрузку;
- размер web build;
- memory usage после 20–30 минут переходов;
- выгружаются ли ненужные большие textures;
- нет ли постепенного роста памяти после повторных переходов;
- animation sheets не загружаются все сразу без причины;
- нет фризов при открытии блокнота/карты;
- audio loops корректно освобождаются/переключаются.

На Пикабу в рекомендациях отдельно подчёркивается быстрая загрузка, ориентир до 10 секунд при нормальном соединении, поэтому тяжёлые ассеты подгружаем по мере необходимости.

---

# 9. Autosave stress test

Сценарии:

1. получить улику → немедленно refresh;
2. завершить puzzle → refresh;
3. открыть новую точку карты → refresh;
4. закрыть вкладку на переходе между сценами;
5. потерять интернет после local save до cloud sync;
6. восстановить интернет;
7. cloud save старее local;
8. cloud save новее local;
9. повреждённый/неподдерживаемый cloud save;
10. SDK временно недоступен.

Ожидаемый результат: максимум теряется текущая незавершённая реплика/анимация, но не смысловой прогресс.

# 10. Яндекс Игры — checklist

Перед каждой submission сверять актуальную документацию.

Обязательно проверить:

- SDK init;
- `LoadingAPI.ready()` вызывается именно когда первый экран готов к взаимодействию;
- gameplay start/stop размечены согласованно с pause/menu/ad;
- pause/resume events;
- звук не продолжает играть в неподходящем состоянии;
- прогресс сохраняется после refresh;
- fullscreen вызывается только в логической паузе;
- warning/transition перед рекламой соответствует актуальным требованиям;
- rewarded никогда не обещает награду без обработки успешного показа;
- debug-mode тест;
- ad blocker / no-fill path;
- anonymous/authorized player path;
- cloud save limits/ошибки.

Официальные страницы для проверки:

- https://yandex.ru/dev/games/doc/ru/concepts/requirements
- https://yandex.ru/dev/games/doc/ru/sdk/sdk-game-events
- https://yandex.ru/dev/games/doc/ru/sdk/sdk-adv
- https://yandex.ru/dev/games/doc/ru/sdk/sdk-player

# 11. Пикабу Игры — checklist

Перед submission сверять актуальную документацию.

Проверяем:

- игра доступна по HTTPS на собственном сервере;
- SDK init ровно один раз;
- `gameStarted()` после готовности первого интерактивного экрана;
- игра доступна без обязательной внешней регистрации;
- русскоязычный интерфейс по умолчанию;
- cloud save работает;
- player ID корректно обновляется после авторизации в текущей сессии;
- signed player data проверяется backend-ом, если используется для save session;
- fullscreen/rewarded pause;
- pause при switching tabs / auth modal / ads;
- audio mute/background handling;
- игра работает при включённом ad blocker;
- desktop + mobile Chrome/Yandex Browser/Safari;
- UI не выходит за viewport.

Официальные страницы для проверки:

- https://games.pikabu.ru/sdk/docs/requirements/tech
- https://games.pikabu.ru/sdk/docs/sdk/init
- https://games.pikabu.ru/sdk/docs/sdk/player
- https://games.pikabu.ru/sdk/docs/sdk/ads
- https://games.pikabu.ru/sdk/docs/sdk/verification

# 12. Реклама — отдельные тесты

### Fullscreen

- показ успешен;
- no fill;
- ошибка SDK;
- пользователь закрыл рекламу;
- повторный вызов слишком скоро;
- игра точно остановлена;
- после close управление возвращено;
- звук возвращён ровно один раз;
- сюжетный state не изменяется из-за результата рекламы.

### Rewarded, если включим

- reward только после подтверждённого условия SDK;
- закрытие раньше времени не ломает hint UI;
- ошибка рекламы не блокирует бесплатный путь прохождения;
- повторный запрос не выдаёт reward дважды.

# 13. Save schema migration test

До первого публичного релиза уже написать migration test хотя бы для `schema_version = 1` → будущего mock `2`.

Причина: после публикации нельзя рассчитывать, что все игроки начинают с чистого сохранения.

При несовместимости:

- не падать;
- сохранить резерв старого state;
- попытаться восстановить акт/facts/items;
- если автоматическое восстановление невозможно, показывать человеческое сообщение, а не stack trace.

---

# 14. Content regression

После любого изменения `STORY`, `PUZZLES` или dialogue data прогоняем минимум:

- старт новой игры;
- GATE-01;
- открытие Книги;
- НИИ → внешний свидетель;
- квитанция;
- ячейка;
- возврат якоря;
- финал;
- второй звонок Лешего.

Изменение одной реплики не должно случайно удалять state effect, который открывает следующую локацию.

---

# 15. Финальная проверка художественной целостности

Перед release lock:

- фон не выбивается по эпохе;
- нет случайной чрезмерно современной техники;
- сказочные существа выглядят частью быта;
- нет визуального копирования известных мультперсонажей;
- подписи читаются;
- все важные props видимы;
- персонажи одинакового масштаба внутри одной сцены;
- тени/свет не прыгают между animation frames;
- нет временных placeholder assets.

---

# 16. Тестовый состав

Минимально полезны разные профили:

1. человек, который регулярно играет в квесты;
2. человек, который почти не играет в point-and-click;
3. мобильный игрок;
4. тестировщик, который намеренно ломает порядок действий;
5. автор/разработчик — только как дополнительный, а не единственный тест.

Особенно важно наблюдать за первым прохождением без подсказок автора.

---

# 17. Метрики первой версии

После публикации отслеживать минимум:

- старт игры → начало дела;
- дошёл до первой большой дедукции;
- дошёл до Книги;
- дошёл до НИИ;
- дошёл до Бурова;
- открыл ячейку;
- завершил игру;
- средняя длительность сессии;
- число сессий до завершения;
- использование hints;
- точки выхода;
- save errors;
- ad show/fail rates.

Цель — понять, где игроки реально теряются или уходят, а не усложнять игру заранее «для удержания».

# 18. Release gates

## Gate A — vertical slice

`Agency → map → Boiler → clue → notebook → save/load` работает полностью с Local adapter.

## Gate B — content complete

Вся история проходится от начала до финала без платформенных SDK.

## Gate C — art/audio complete

Нет обязательных placeholders.

## Gate D — platform complete

Яндекс и Пикабу adapters, cloud saves, lifecycle и ads протестированы.

## Gate E — moderation build

Чистый production export, debug UI отключён, promo assets готовы, требования площадки перепроверены.

---

# 19. Что считается релизом 1.0

Игра считается готовой, когда:

- сюжет завершён и не обрывается;
- минимум 30 минут реального прохождения обеспечены с большим запасом;
- все обязательные головоломки честные;
- сохранение переживает reload;
- mobile/desktop поддержаны;
- звук/пауза работают корректно;
- платформа не обязательна для работы core logic;
- нет критических/soft-lock багов;
- рекламы не ломают историю;
- финальная сцена с Лешим работает как тизер, но первое дело полностью закрыто.
